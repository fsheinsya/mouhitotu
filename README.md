# 毛一つ

unity1week（お題「もうひとつ」）参加作品。神様の毛を集めてポイントを獲得し、アイテムで収集効率を強化していく収集系ブラウザゲームです。

## 公開URL

ブラウザ上でプレイできます。
[unityroomでプレイする](https://unityroom.com/games/mouhi1tsu)

- 使用技術：Unity / C# / ScriptableObject / WebGL

## 概要

プレイヤーは時間経過で生えてくる毛をドラッグで収集してポイントを獲得し、そのポイントでアイテムを購入します。
育毛剤で毛の生成速度が上がり、高級育毛剤でレアな毛が出やすくなります。
お題「もうひとつ」から「もう一本」という発想を広げた、コミカルなテーマの短時間ゲームです。

## 生成AIの使用について

生成AIは、実装方針の整理やコード作成の補助として活用しました。
ゲームのコンセプト、仕様設計、データ構成、バランス調整は自分で考え、出力されたコードも動作確認しながら修正しました。

## 設計として意識したこと：マスターデータと実行時データの分離

前作（Slot）で出現率や調整パラメータをコードに直書きし、調整のたびにコードを触る羽目になった反省から、今回は「ゲームのデータをコードから引き剥がす」ことをテーマにしました。

- `ItemData` / `ItemMasterData`：アイテムの名前・価格・在庫・効果量を`ScriptableObject`で定義
- `MissionScriptable` / `MissionDataScriptable`：ミッションの定義（ID・達成条件・説明文）を`ScriptableObject`で定義

アイテムやミッションの追加・数値調整をアセットの追加・編集だけで完結させ、コードを変更せずにバランス調整できる形を目指しました。

ミッションについては、`MissionScriptable`（定義）から実行時用の `MissionData.Mission`（達成状態を持つコピー）を生成する構造にし、「定義は読み取り専用、状態は実行時のコピーが持つ」という運用を意識しました。

## コードを読み返して見つけた問題

提出後に自分のコードを読み返し、分離したつもりで分離しきれていない箇所や、単純なバグを複数見つけました。

### ScriptableObject（マスターデータ）を実行時に書き換えていた

ミッションでは「定義→実行時コピー」の分離をしたのに、アイテムでは `ItemData.stock--` とScriptableObjectの在庫を直接減算しています。
マスターデータを実行時に書き換えると、エディタ上では値が保存されてしまい、自分で立てた「定義は読み取り専用」という方針と矛盾します。同じ方針をプロジェクト全体で貫けなかったのが一番の反省点です。

### シングルトンの生存判定が逆

`GameParameter.Awake()` で `if (Instance == null) { Destroy(gameObject); return; }` と書いており、最初のインスタンスが自分自身を破棄してしまうため、`Instance` が設定されません。
正しくは `if (Instance != null)` です。制作当時は参照エラー（NullReferenceException）に苦労しましたが、その原因の一つを自分で作り込んでいたことに、今回読み返して気づきました。

### 通貨の二重管理

スコア（通貨）を `ScoreSystem.score` と `ItemSystem.currentScore` の2箇所で別々に持っており、「集めたポイントで買い物をする」という仕様がコード上では繋がっていません。
ゲーム内で共有される状態は、単一の管理元に集約すべきでした。

### 引数と同名のフィールド

`countSystem.AddCount(int count)` 内の `count++` は引数の方をインクリメントしており、フィールドが増えません。命名の衝突に気づけていませんでした。

### MonoBehaviour を `new` で生成

`MissionData` が `MonoBehaviour` を継承したまま `new` で生成されています。実行時データを持つだけのクラスは純粋なC#クラスにすべきでした。

### Git管理の不備

制作後のGit管理・バックアップに課題があり、完成版の一部（毛のレア度別データ・重み付き抽選・図鑑まわり）をリポジトリに反映できていません。
リポジトリに残っているのは主要な実装の一部で、完成版はunityroomの公開ビルドで確認できます。

## 学んだこと

- マスターデータと実行時データの分離は、「方針を立てること」より「全箇所で貫くこと」の方が難しい
- 共有状態は一元管理しないと、仕様がコード上で繋がらなくなる
- 自分のコードは自分では読み返さないとバグに気づけない。特にシングルトンの初期化条件のような「動いているように見えて壊れている」コードは要注意
